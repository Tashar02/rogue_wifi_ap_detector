\begin{abstract}
Wireless network security in resource-constrained IoT environments demands proactive intrusion detection and resilient access extension. This paper presents a hardware-integrated Rogue Wi-Fi Access Point Detector built on the RISC-V ESP32-C6 platform \cite{esp32c6}, broadcasting under the SoftAP SSID \texttt{Scarlet ESP32-C6}. The system runs six operational modes: promiscuous frame interception, targeted ping monitoring, real-time AP traffic analysis, client station MAC logging, Denial-of-Service (DoS) traffic flood detection, multi-port honeypot deception across FTP, SSH, HTTP, and HTTPS, and an automated Layer-3 Network Address and Port Translation (NAPT) Wi-Fi repeater \cite{napt_ref}. A state-driven single-button control mechanism, non-blocking asynchronous timing, active acoustic feedback, and dual OLED \cite{ssd1306} and addressable RGB visual telemetry \cite{neopixel} constitute the hardware interface. Empirical evaluation demonstrates low-latency packet inspection, rapid honeypot connection termination, dynamic RSSI-based open network selection, and reliable packet routing under active flood alerts.
\end{abstract}

\section{Introduction}
Wireless local area networks (WLANs) built on IEEE 802.11 standards \cite{ieee80211} are the backbone of contemporary IoT deployments. Their open-medium transmission model exposes them to malicious probes, address spoofing, Denial-of-Service (DoS) floods, and unauthorized port reconnaissance. Enterprise networks deal with this through centralized Intrusion Detection Systems and dedicated honeypots running on high-performance servers. Edge nodes and small-scale field setups have no real equivalent: there is no lightweight, battery-operable device that can monitor threats and extend network reach at the same time.

The ESP32-C6 opens up new ground for this kind of tool. Its 32-bit RISC-V core comes with integrated $2.4\,\text{GHz}$ Wi-Fi 6 (802.11ax) and Bluetooth 5 (LE) \cite{esp32c6}, and its raw packet capture API \cite{espressif_idf} sits alongside a full LwIP TCP/IP stack \cite{lwip}. A single chip can act as a network monitor, a decoy target, and an Internet bridge at the same time.

This paper presents the \textbf{Rogue Wi-Fi Access Point Detector} (SSID \texttt{Scarlet ESP32-C6}), a multi-functional wireless security sentry and bridge. A debounced multi-click physical interface and I2C display peripherals drive six execution modes: targeted ICMP/data packet sniffing, high-throughput traffic monitoring, station connection logging, frame flood alarm, active TCP honeypots on industrial ports, and an LwIP NAPT Wi-Fi range extender \cite{napt_ref}.

\section{Related Work}
Wireless security monitoring at the embedded edge has evolved through specialized firmware. Early work used ESP8266 and ESP32 microcontrollers for frame injection or passive packet capture \cite{espressif_idf}. Portable security tools typically cover one domain: passive network sniffer, standalone rogue access point, or software repeater.

Hardware honeypots have traditionally required Linux-based single-board computers running full software suites. Microcontroller-based honeypots are scarce, constrained by limited memory and simplified TCP/IP stacks \cite{honeypot_iot}. Wi-Fi repeater solutions on microcontrollers typically operate at Layer 2 or require static routing, and none integrate automated open-network discovery with Layer-3 NAPT and real-time security monitoring inside a single non-blocking state machine.

The Rogue Wi-Fi AP Detector consolidates promiscuous frame analysis, active TCP honeypots, station logging, and LwIP NAPT routing on a single low-power RISC-V chip.

\section{Problem Statement}
Portable wireless security tools carry four recurring operational deficits:
\begin{enumerate}
    \item \textbf{Single-Function Constraints:} Most embedded security devices perform frame sniffing or AP spoofing in isolation, with no network bridging or deception capability in the same unit.
    \item \textbf{Heavy Resource Overhead:} Software-defined wireless monitoring solutions depend on resource-heavy operating systems, ruling out compact deployment and immediate cold-boot readiness.
    \item \textbf{No Local Physical Alerting:} Threat notifications route to remote web dashboards. Field engineers get no acoustic or visual feedback when RF traffic anomalies or port scans occur on-site.
    \item \textbf{Bridging Limitations:} Standard Wi-Fi repeaters lack security auditing of connected SoftAP clients and signal-strength-driven automatic connection to open access networks.
\end{enumerate}

\section{Methodology}

\subsection{System Overview \& Control Architecture}
The hardware consists of an ESP32-C6 microcontroller \cite{esp32c6} interfaced with an SSD1306 $128 \times 64$ OLED display \cite{ssd1306} over I2C, a passive buzzer, dual indicator LEDs (Blue for activity, Orange for warning), an onboard WS2812 addressable RGB LED \cite{neopixel}, and a push button.

The firmware processes button input through a non-blocking debounced state machine supporting three gestures: short single clicks for menu navigation, double clicks to exit a feature and return to the main menu, and long presses ($\ge 1000\,\text{ms}$) to launch the selected feature. \subsection{Hardware Circuit Interfacing}
GPIO pin assignments are optimized for the ESP32-C6 pinout \cite{esp32c6}:
\begin{itemize}
    \item \textbf{Buzzer Output:} GPIO 0 (PWM frequency generation)
    \item \textbf{Button Input:} GPIO 1
    \item \textbf{Blue Activity LED:} GPIO 2
    \item \textbf{Orange Warning LED:} GPIO 3
    \item \textbf{Addressable RGB LED:} GPIO 8 (NeoPixel single-wire signal \cite{neopixel})
    \item \textbf{I2C Bus:} GPIO 6 (SDA) and GPIO 7 (SCL) at $400\,\text{kHz}$
\end{itemize}

Each active component (the buzzer, the push button, and both indicator LEDs) connects through a dedicated $1\,\text{k}\Omega$ resistor since they are quite fragile components and there's always a chance to get more voltage into them and burn them accidentally.

\subsection{Software Architecture \& Feature Execution}
The firmware runs an asynchronous event loop over six distinct execution states, built on the Arduino framework for ESP32 \cite{arduino_esp32}.

\subsubsection{Feature 1: AP Ping Monitor}
Sets the Wi-Fi stack into promiscuous mode via \texttt{esp\_wifi\_set\_promiscuous()} \cite{espressif_idf}. The callback \texttt{sniffer\_callback()} parses incoming IEEE 802.11 \cite{ieee80211} data frames, matching destination MAC addresses against the module's SoftAP MAC. Packet throughput above $10\,\text{pkts/sec}$ triggers a Yellow RGB warning and a single $2400\,\text{Hz}$ acoustic tone.

\subsubsection{Feature 2: AP Data Monitor}
Tracks cumulative packet counts ($\text{Total Rx}$) and interval throughput at $200\,\text{ms}$ resolution. RGB brightness scales with packet activity to give a real-time visual indication of payload transfers.

\subsubsection{Feature 3: Client Logger}
Binds to \texttt{ARDUINO\_EVENT\_WIFI\_AP\_STACONNECTED} events \cite{arduino_esp32}. On station association, the client MAC address is parsed, formatted into standard hexadecimal notation, written to the display buffer, and flagged with a $2400\,\text{Hz}$ tone.

\subsubsection{Feature 4: Flood Monitor}
Counts data frame arrivals over 1-second windows. Frame rates above $\text{FLOOD\_THRESHOLD} = 100\,\text{pkts/sec}$ trigger a high-priority alarm: a $2500\,\text{Hz}$ siren, critical-red RGB, and a warning on the OLED interface.

\subsubsection{Feature 5: Port Scan}
Opens four simultaneous \texttt{WiFiServer} \cite{arduino_esp32} listeners on FTP (21), SSH (22), HTTP (80), and HTTPS (443). Each inbound connection is accepted, flushed, and closed immediately to prevent resource exhaustion \cite{honeypot_iot}. A hit triggers a non-blocking 3-second alternating siren ($1800\,\text{Hz}$--$2800\,\text{Hz}$) with red-purple RGB strobing.

\subsubsection{Feature 6: NAPT Wi-Fi Repeater}
Runs in dual AP+STA mode (\texttt{WIFI\_AP\_STA}) \cite{espressif_idf}. The user selects either a pre-configured target SSID (WPA2 credentials) or an asynchronous scan for open networks. In open scan mode, the device ranks surrounding open APs by RSSI and connects to the strongest.

After STA connection succeeds, the firmware enables Layer-3 NAPT within the LwIP stack \cite{lwip}:
\begin{equation}
\mathtt{ip\_napt\_enable}\left(\mathtt{softAP\_IP}, 1\right)
\end{equation}
NAPT instantiation runs inside \texttt{LOCK\_TCPIP\_CORE()} and \texttt{UNLOCK\_TCPIP\_CORE()} blocks \cite{lwip} to prevent race conditions against active packet traffic. The SoftAP DHCP server then reconfigures to push the upstream STA DNS address to connected clients, falling back to Google DNS $8.8.8.8$ when no valid upstream DNS is available \cite{napt_ref}.

Promiscuous frame filtering parsed IEEE 802.11 \cite{ieee80211} data packet headers without triggering buffer overflows or execution stalls. Flood conditions for the Flood Monitor (F4) were generated using the PingTools application \cite{pingtools} on Android, directed at the device's SoftAP interface; packet rates consistently exceeded $100\,\text{pkts/sec}$ and triggered the critical alarm state. Port Scan (F5) testing used PingTools port scans \cite{pingtools} against ports 21, 22, 80, and 443: all connections were detected and the alternating siren fired in under $3\,\text{ms}$, with no impact on the non-blocking state loop.

WiFi Repeater (F6) open-network acquisition took $4.613\,\text{s}$ to lock onto the strongest open access point (RSSI $-30\,\text{dBm}$). The subsequent NAPT and DHCP/DNS reconfiguration completed in under $1\,\text{ms}$, confirming the operation runs synchronously in memory. \texttt{LOCK\_TCPIP\_CORE()} prevented LwIP stack panics during dynamic DNS reallocation \cite{lwip}.

\section{Challenges Faced}
Developing and debugging the unified firmware on ESP32-C6 hardware exposed four critical integration challenges:

\begin{enumerate}
    \item \textbf{Hardware Serial Debugging vs. Native USB CDC:} Serial output failed to stream or hung on startup. The ESP32-C6 native USB-CDC driver conflicted with the hardware UART peripheral \cite{espressif_idf}. Disabling USB CDC on Boot in the Arduino IDE build flags re-routed \texttt{Serial.print()} over the hardware UART, restoring serial telemetry.
    \item \textbf{Wi-Fi Stack Mode Transitions:} Switching the radio between promiscuous AP mode (\texttt{WIFI\_AP}) and dual repeater mode (\texttt{WIFI\_AP\_STA}) corrupted internal ESP-IDF driver structures \cite{espressif_idf}. An explicit teardown sequence calling \texttt{WiFi.mode(WIFI\_OFF)} and detaching sniffer callbacks before re-initializing Wi-Fi resolved the corruption.
    \item \textbf{LwIP Thread Safety \& Core Locking:} Calling \texttt{ip\_napt\_enable()} while active client packets traversed the interface caused memory panics \cite{lwip}. Wrapping network interface initialization inside \texttt{LOCK\_TCPIP\_CORE()} and \texttt{UNLOCK\_TCPIP\_CORE()} eliminated the race condition.
    \item \textbf{Non-Blocking Multi-Peripheral UI Execution:} Passive buzzer PWM sweeps, WS2812 color transitions \cite{neopixel}, SSD1306 display updates \cite{ssd1306}, button debouncing, and multi-port honeypot polling all had to run without blocking \texttt{delay()} calls. A \texttt{millis()}-based timestamp engine with per-feature interval counters handled the coordination.
\end{enumerate}

\section{Conclusion}
The Rogue Wi-Fi Access Point Detector runs multi-layered wireless security monitoring, active deception, and network bridging on a single low-power RISC-V microcontroller at under \$13 in hardware cost. Promiscuous frame sniffing, flood alarms, multi-port honeypots, and LwIP NAPT repeating operate concurrently within a single non-blocking state machine, giving field engineers a self-contained tool for wireless auditing and network extension. Future work will add Bluetooth Low Energy (BLE) attack detection, battery management telemetry, and cloud reporting over MQTT.
